# World-model source decision for rover height scans

Research resolution for [Which upstream world-model implementation fits action-conditioned rover navigation?](https://github.com/sameeerkashyap/mars-world-rover/issues/6), 2026-11-21.

## Decision

Use the pinned **main AdaLN JEPA-WM predictor** for the next discriminating pilot. Compare it with the pinned **DINO-WM predictor** on the same unwarped rover features and action history. Keep motion-only transport and the scan-aware planner as controls. The existing rover model is a transport-plus-residual DINO-WM adaptation. It does not test the main AdaLN implementation. Do not use a DROID or PointMaze dynamics checkpoint as rover dynamics. This is an implementation choice for an experiment, not evidence that AdaLN improves navigation. [S1–S5, R1–R3]

The smallest first decision is whether a learned predictor adds useful action-dependent terrain information beyond transport. A new image encoder, large search sweep, or full simulator retraining campaign is not needed to answer that question. The exact pilot below is a proposed rover adaptation. Its values are candidates, not measured optima.

## What each upstream implementation actually does

| --- | --- | --- | --- |
| Observation encoding | Sim defaults: frozen DINOv2 ViT-S/14, 224 pixels, 16×16 spatial patches, 384 values per patch. DROID main model instead uses DINOv3-L/16. | Sim defaults use the same frozen DINOv2-S/14 patch features; no pooling to one global vector. | Fixed DROID default: frozen V-JEPA-2-G/16, 256 pixels, 16×16 patches, 1408 values per patch. Each image is duplicated into a two-frame tubelet and encoded as a frame, with representation layer normalization. |
| Predictor | `VisionTransformerAdaLN`; linear visual input/output projections; transformer blocks with rotary position encoding. | `ViTPredictor`; learned position embeddings and frame-causal attention. Factory uses feedforward width 2048 and dropout 0.1. | `VisionTransformerPredictorAC`; visual input/output projections, rotary positions, frame-causal transformer blocks. |
| Action conditioning | Raw action block is projected to the block width. At **every block**, an action-dependent linear map gives six vectors: attention and feedforward shift, scale, and residual gates. These are repeated over that frame's spatial patches. Despite config `action_conditioning: token`, the action is used for modulation; it is not appended as an action token. | A trainable action encoder supplies features repeated at every spatial patch and joined on the **feature axis**. Proprioception is joined in the same way when enabled. Action features are split back out of predictor output. | Token mode prepends a learned action token per frame, plus optional proprioception/extrinsics tokens. Feature mode also exists, but the fixed DROID config uses token mode. |
| Proprioception | Sim reference uses a 16-value trainable embedding joined to visual features; predictor can output its next embedding. Encoder frozen. | Predictor/action projection trained during DROID post-training; encoder frozen. “Fixed” means the training-loss bug was corrected, not that all predictor weights were frozen during training. |
| Reference rollout training | Sim AdaLN: squared feature error, two predicted intervals, detached rollout inputs, random prefix, context up to three frames. | Sim reference: squared feature error and one predicted interval (teacher forcing). | Fixed DROID: absolute feature error, two predicted intervals, no stop-gradient through rollout, first prefix, up to eight-frame training context. |

Each cell is grounded in the model implementations, construction code, and exact configs [S1–S8]. A configured `use_rope: true` in a DINO-WM YAML does not change `ViTPredictor` into a rotary-position model: the DINO factory does not pass that flag to it. AdaLN initialization defaults to modulation weight scale factor 10; this is distinct from its optional zero initialization. Do not silently substitute AdaLN-zero. [S1, S2, S4]

The shared mask helper permits attention to all patches and condition tokens in the current frame and earlier frames, but no later frame. Prediction is shifted by one frame, so the current input frame is legitimate context for its next-frame target. The helper sets its own temporal window to the configured sequence depth; it does not implement an additional sliding local-time cutoff from `local_window_time`. The caller's context slice provides the rollout window. [S2, S3, S9, S10]

`VideoWM.compute_loss` compares next-frame visual features, plus predicted proprioception when enabled, using configured L1/L2/cosine/smooth-L1 weights. There is no default reward or collision loss. Training first computes the teacher-forced next-frame loss, then adds autoregressive losses when `rollout_steps > 1`. The training loop passes `rollout_steps - 1` into `VideoWM.rollout`; thus config value 2 means one base prediction and one further prediction. The rollout target starts at `t+2` after the first prediction. Copying the wrong target index can recreate the published reproduction problem. [S9, S10]

The JEPA-WMs authors report that the original V-JEPA-2-AC two-step loss matched the second prediction to the wrong time target. They retrained the fixed baseline. Use `vjepa2_ac_droid`, not `vjepa2_ac_oss`, to mean that fixed checkpoint. This is an authors' report, not an independent reproduction here. The original V-JEPA-2 paper concerns tabletop end-effector control from fixed external cameras; it does not establish rover height-scan transfer. [P1 §B, P3 §3, S11]

The DINO-WM paper uses frozen spatial features, action-conditioned frame-level autoregressive prediction, and image-goal planning. An optional visual decoder is for interpretation and is trained separately. These are useful design ideas; the paper's benchmark results do not establish performance on metric height scans. [P2 §§3.1–3.2]

## Interfaces and checkpoints

`VideoWM.encode_obs` consumes a dictionary with `visual` shaped `[batch,time,channels,height,width]` and optional `proprio`. Its latent visual form is `[batch,time,views,grid_h,grid_w,features]`. `encode_act` consumes action sequences, groups commands to the model interval, and returns raw action blocks when `action_encoder_inpred` is true. `forward_pred` dispatches to each predictor, returns visual/action/proprioception features, and keeps the three conditioning schemes separate. For a rover block of five two-value commands, raw action width is **10**, not 2. The upstream training code derives width as dataset action width × encoder tubelet size × frame skip ÷ action skip. [S9, S10]

The planning wrapper `EncPredWM.encode` accepts raw visual observations, applies `/255` and training transforms, and returns latent tensors or a TensorDict. `unroll(z_ctxt, act_suffix)` takes actions in `[time,batch,action_width]`, predicts with a sliding context, and returns a time-major sequence including initial context. It optionally updates proprioception by prediction or DROID-specific `compute_new_pose`. It is not a drop-in rover history wrapper: action/observation alignment and initial context lengths must be tested, and already normalized height tensors must not be divided by 255 again. Its unroll builds action history from the supplied suffix, so two measured context frames need an explicit aligned historical action block. The existing rover history code already records that block. Reuse that timing convention in a small predictor adapter; do not copy DROID pose integration. [S12, R2]

Torch Hub returns `(model, preprocessor)`. The main model entries include PointMaze/Wall/Push-T/Metaworld and DROID; DINO-WM provides the same environment families; fixed V-JEPA-2-AC provides DROID/RoboCasa. These dynamics checkpoints encode each environment's observation and action conventions. Use the pretrained **encoder** with a rover-trained predictor. Loading `jepa_wm_pointmaze` or changing a DROID checkpoint's action input width is not a valid rover transfer experiment. Image decoders are unnecessary for training or latent planning. [S0, S11]

## Native planning objective and search

Upstream planning predicts features under candidate **action sequences** and minimizes distance to an encoded **goal observation**. It supports terminal squared distance (L2), absolute distance (L1), and negative cosine similarity, with optional proprioception weight `alpha`; `sum_all_diffs` switches from terminal cost to accumulated cost. The target-distance objectives do not themselves charge collision, roughness, action effort, or goal distance in metres. Their action argument is unused. [S13]

Search implementations include CEM (cross-entropy method: repeatedly sample sequences, keep low-cost samples, and update their Gaussian mean and spread), Nevergrad, plain gradient descent, Adam, and MPPI. The PointMaze CEM reference uses horizon 6, context 2, 30 iterations, 300 samples, 10 elites, spread 1.0, terminal L2, and six actions stepped before replanning. This is an upstream benchmark setting, not a latency recommendation for this rover. The config has `alpha: 0` before evaluation-time overrides; other evaluation files/launch settings can enable proprioception. Always record the resolved config. [S14, S15]

The current rover controller does something different: it first rejects unsafe candidates using the measured scan, uses a scan-derived route and frozen goal-motion model, then optionally adds `0.25 × maximum predicted central terrain cost` across active one-to-five-second horizons. The readout estimates a height-rule blocked-area fraction. That fraction is not a calibrated collision probability. Thus upstream image-goal CEM results cannot validate this reranking objective. [R2, R3]

Height scans are local and move with the rover. Two safe flat places can have very similar scans even when one is far from the goal. Conversely, a goal scan can differ because of viewpoint or occlusion. A scalar goal location does not provide the goal observation that native feature-distance planning needs. Therefore, do not invent an all-flat target scan or access a hidden goal scan to make latent planning run. Keep physical goal error and measured-scan rejection for the first navigation test. If image-goal planning is later tested, obtain the goal observation through an allowed map/sensor interface, define its availability before evaluation, and report it as a separate objective. This is a task-specific inference from the interfaces, not a paper result. [S13, R2, R3]

## What the completed rover evidence establishes

The inspected `RoverJEPA` uses frozen DINOv2-S/14 at 112 pixels, 64 patches, and a train-only PCA projection from 384 to 64 feature values. A two-layer width-96 `ViTPredictor` receives those 64 values plus 16 previous-command and 16 action values. It learns a feature correction to frozen motion-based spatial transport. Goal pose is advanced by frozen motion; the computed pose loss is logged but not added to the optimized loss. Its 167,904 trainable parameters are therefore not the main upstream AdaLN model and do not learn a new goal-motion predictor. A shuffled-action test also perturbs the motion transport, so passing it alone cannot isolate learned action use. [R1]

The completed paired comparison found development success counts of scan-aware **4/6**, transport **3/6**, and JEPA **4/6**. All had zero collisions and two stalls. On six fresh cases, counts were **5/6**, **6/6**, and **6/6**, all with zero collisions and zero stalls. Mean planning latencies were 43.24, 55.01, and 67.51 ms. The baseline's sole fresh miss ended at 0.1803140759 m against the fixed `<0.18 m` threshold. This is not evidence of an obstacle-handling gain. JEPA did not separate from transport on success. The small sample and already inspected layouts cannot support a final generalization claim. See the archived [completed-experiment resolution](https://github.com/sameeerkashyap/mars-world-rover/issues/5#issuecomment-7069614422). [R4]

## Smallest discriminating pilot

Run this as staged work. No GPU workload was launched for this research.

1. **Assert the interface on CPU first.** With synthetic tensors, check finite forward/backward outputs, action width 10, 8×8 patch ordering, exact historical action timing, and one-/two-/five-interval target indices. Change only a later context frame/action and assert that earlier outputs do not change. Change the first future command block and check which output interval first changes. Reload a checkpoint and reproduce predictions. For DINO, its module-level `NUM_FRAMES`/`NUM_PATCHES` globals mean differently shaped predictors in one imported module need care; run each arm separately. [S1–S3, S9, R1]
2. **Fit two unwarped learned arms on the same frozen features.** Use existing episode/layout splits, fixed physical height normalization, two context observations one second apart, and five actual 0.2-second commands per interval. Use full cached 384-value DINO features at 112 pixels (64 patches) first. This avoids a fresh encoder pass and removes the existing 64-value PCA bottleneck from the conditioning test. Train only predictors and command encoders. No motion warp, transported residual, or future measured state enters either learned arm. Keep frozen motion for external goal propagation and the transport control. This tests learned terrain dynamics, not learned pose dynamics. [R1, R2]
3. **Use a small explicit architecture pair.** AdaLN: visual input/output width 384, predictor visual width 384, previous-command feature width 16, total block width 400, action projection from 10 to 400, depth 2, four heads, rotary positions, nonzero upstream AdaLN initialization. DINO: visual 384 + previous-command 16 + action 16 = 416 total values, depth 2, four heads with explicit head width 104, feedforward width 2048 and dropout 0.1 as in its factory. Use trainable linear command embeddings. Previous command is a known controller input: during rollout set it from the last command in the preceding candidate block, not a future measurement. Do not include goal distance/bearing as visual target features. Report trainable parameter counts and memory; this pair compares implementations, not exactly matched capacity. AdaLN has extra modulation/projection parameters. It is a reduced-depth upstream adaptation, not a reproduction of a published checkpoint. [S1–S4, R1]
4. **Train two predicted intervals before expanding.** Start at AdamW learning rate `3e-4`, batch 16, clip norm 1, maximum 60 epochs, and validation patience 8, matching the current rover training envelope. Use squared full-feature error, identical train-only normalization for both arms, and equal per-horizon reduction. Detach predicted rollout inputs as in the main upstream sim setting. Select checkpoints on held-out validation error at both one and five intervals, then inspect the test split once. Keep copy, transport, and cross-episode shuffled-action results on original full features. Compare action-swap degradation in each learned arm against its own unshuffled forecast, as transport is absent from these arms. Report per-layout error and near-rover hazard-region error, not only the average over flat patches. [S5, S6, R1]
5. **Require a signal before a simulator test.** Predeclare a practical gain such as at least 2% lower error than transport at both one and five intervals, plus degradation under shuffled future actions, in held-out episodes; the current 2% threshold is a candidate inherited from `quality_passed`, not a statistical confidence claim. Check that dangerous terrain predictions/readout ordering also improve. If transport remains better, stop model scaling and inspect whether scans contain new terrain information beyond rigid motion. If the pair is close, repeat seeds 1 and 2 before naming a winner. Reusing the old readout on a changed feature distribution needs verification or a separately fitted, frozen readout with identical data/protocol. [R1–R3]
6. **Only then run a paired navigation pilot.** Freeze source, weights, normalization, readout, candidates, safety rejection, and cases. Compare scan-aware, transport, and selected learned forecasts on the already inspected development layouts. Start forecast weight at 0.25 and horizon 5 seconds to match completed evidence; include weight 0 as the sanity control. Compare success, collisions, stalls, path length, and mean/p95 end-to-end latency. Reserve new layouts for a later final test; do not tune on them. Promote only with physical navigation evidence and a stated latency budget. [R3, R4]

This pair is the minimum **source-faithful discriminating** test, not the absolute smallest network. If full 384-value features are infeasible, use the existing PCA features in both arms first, clearly label the result as a conditioning screen, and repeat a winning result on full features before rejecting either upstream model. Do not compare a full-feature AdaLN arm against a PCA-only DINO arm and attribute the difference to conditioning.

## Bounded hyperparameter candidates

| Question | First setting | Next candidates only when needed | Reason and limit |
| --- | --- | --- | --- |
| Learning rate | `3e-4` | `1e-4` if unstable; `5e-4` if underfitting | Current rover anchor versus upstream sim `5e-4`; `1e-5` is not a source-backed default for a newly initialized predictor. |
| Training rollout | 2 intervals | 1 as a controlled ablation; 5 only if five-interval drift remains | Main upstream uses 2, DINO reference uses 1. Change one factor at a time; never conflate “2” with two extra intervals. |
| Depth | 2 | 6 after a useful signal or clear underfit | Current cheap rover scale versus upstream sim depth 6. More depth is not established as useful here. |
| Context | 2 one-second frames | 3 as a separate ablation | Existing live history supports 2; source sim training uses 3 and planning often uses 2. A longer context changes history needs. |
| Encoder resolution | 112 pixels | 224 pixels separately | 112 reuses current cache; 224 matches source and quadruples patch count. New resolution requires new feature cache and readout validation. |
| Forecast cost weight | 0.25 plus 0 control | 0.1, then 0.5 only if ordered costs help | These are rover-specific candidates; no source paper establishes them. |
| Planning horizon | 5 seconds | 1 or 3 seconds if forecast error grows | Existing forecast contract supports 1–5. Keep command interval and action bounds fixed. |
| Search | Existing candidates | CEM only after objective works | Source CEM 30×300 samples is an anchor for reproduction, not a rover real-time default. Measure latency before adopting it. |

Do not run the Cartesian product. Resolve one decision at a time. Keep seed, data, optimizer/RNG state, source hashes, and selected epoch with every run. Epoch limits and validation early stopping are acceptable; no Nautilus wall-clock deadline, timeout wrapper, or automatic timed deletion is proposed.

## Checks and limits

Read the pinned implementations, their construction paths, training/evaluation configs, current rover training/inference code, paper sections, and completed-evidence resolution. No source code, running job, checkpoint, or user-worktree file was changed. No GPU test or new benchmark was run. The proposed tensor dimensions and adapter still need the CPU checks above before training; this note does not claim that the unmodified upstream planning wrapper supports rover history. No paper establishes an optimum for this rover, and the completed trials do not show a learned benefit over transport.
